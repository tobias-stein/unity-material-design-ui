# Code Review — 2026-09-29

## Critical Issues

### 1. Thread Safety — `Pool<T>` and `PoolAsync<T>`
`List<T>` is not thread-safe. `get()`/`free()` mutate `available` and `pool` without synchronization. If called from multiple threads (e.g., `UniTask` continuations), the lists can corrupt.

**Fix:** Use `ConcurrentBag<T>` or add `lock` statements around all mutations.

### 2. Thread Safety — `Binder<TData>._dependencies`
`Dictionary<string, List<string>>` is accessed from `bind()` and `refreshBinding()` without synchronization. Concurrent binding + refresh = crash.

**Fix:** Use `ConcurrentDictionary` or add locking.

### 3. Unbounded Memory Growth — `BinderCache`
Static `ConcurrentDictionary` caches every property getter/setter per type — forever. Never evicted.

**Fix:** Use a bounded cache (e.g., `MemoryCache` with size limit) or clear on domain reload.

### 4. Unbounded Memory Growth — `_pendingViewContexts`
Every unique view type ever pushed gets a context cached permanently. Push 100 view types = 100 contexts + their mainViews in memory forever.

**Fix:** Add a size limit (e.g., keep max 5 pending contexts per type, or use a LRU cache).

### 5. Missing Null Checks — `ViewContext.setActive`
`mainView` can be null (e.g., if `setMainView` was never called). `DOTween.Kill(mainView.rectTransform)` will NPE.

**Fix:** Add `if (mainView == null) return UniTask.CompletedTask;` guard.

### 6. Missing Null Checks — `UIBootstrapper`
- `Resources.Load<UISettings>` can return null if asset is missing
- `Camera.main` can be null if no camera exists
- No handling of domain reload — old `UI` instance's `ViewManager` and `CancellationTokenSource` leak on script reload

**Fix:** Add null guards, implement `IDisposable` pattern for domain reload cleanup.

## Performance Issues

### 7. `applyUISettings` — Full UI Rebuild on Theme Change
Iterates **all** non-pooled elements, calls `setupUI()` + `refresh()` on each. For large UIs (100+ elements), this causes a frame hitch. The `Debug.Log` with timing is left in production code.

**Fix:**
- Remove `Debug.Log` or wrap in `#if UNITY_EDITOR`
- Consider dirty-flag pattern: only rebuild elements whose theme-relevant properties actually changed
- Spread rebuild across multiple frames for large UIs

### 8. `Pool<T>.free()` — O(n) Validation
`pool.Contains(pooledItem)` is O(n) for large pools.

**Fix:** Use `HashSet<T>` for O(1) lookup, or track state with a flag on the object itself.

### 9. `UIView.show()` — Forced Layout Rebuild
`LayoutRebuilder.ForceRebuildLayoutImmediate(rectTransform)` is expensive and called every time a view is shown, even if layout hasn't changed.

**Fix:** Only call if layout is dirty, or remove and let Unity's layout system handle it naturally.

### 10. `UI.invalidateCache()` — End-of-Frame Rebuild Cost
`GetComponentsInChildren<IUI>(true)` traverses the entire UI hierarchy. If many elements are created/destroyed in one frame, the single end-of-frame rebuild could cause a hitch.

**Fix:**
- Consider incremental cache updates (add/remove single elements) instead of full rebuild
- Or spread the rebuild across multiple frames

### 11. `UIBase.create()` — No Cancellation Support
If the calling method is cancelled (e.g., scene change), the component is still fully created, registered, and activated. The `postConstruct` callback runs even after cancellation.

**Fix:** Accept a `CancellationToken` parameter and check it before each step.

### 12. `Binder.updateField()` — No Equality Check
Always creates a new struct and triggers refresh, even if the value hasn't changed. For frequent updates (e.g., slider drag), this causes unnecessary allocations and UI updates.

**Fix:** Add `EqualityComparer<TValue>.Default.Equals(old, new)` check before proceeding.

---

## Design Flaws

### 13. `ViewTransitionEffects` — All No-Ops
`transitionIn()` and `transitionOut()` return `null`. The `ViewTransition` flags enum is defined but never used. All view transitions are instant — no animation.

**Fix:** Uncomment and fix the composite sequence logic, or remove the dead code.

### 14. `UIView.close()` — Doesn't Actually Dispose
Only fires `onClose` event. Actual disposal is left to `ViewManager`. This is confusing API design — `close()` implies cleanup.

**Fix:** Either make `close()` actually dispose, or rename to `onCloseRequested()` for clarity.

### 15. `UIBase.create()` — Silent Failure When No Active Context
If `UI.views?.currentContext` is null, the element is never registered with any `ViewContext`. It won't be disposed when views close — memory leak.

**Fix:** Log a warning, or throw if no context is available (unless it's a view itself).

### 16. `UI._current` — Not `volatile`
Static field read from multiple places. In theory, if `Dispose()` is called from a different thread, there could be visibility issues.

**Fix:** Mark as `volatile` or use `Interlocked` for assignment.

### 17. `UI._uiComponentTypes` — Reflection in Static Constructor
Reflects over all types in the assembly on first access. Slow startup, and includes all types even if most are never used.

**Fix:** Use a source generator or explicit registration list.

### 18. `ViewContext` — Not Pooled
Reference type created/disposed frequently. Could benefit from pooling to reduce GC pressure.

**Fix:** Pool `ViewContext` instances alongside the view stack.

## Code Quality Issues

### 19. Debug.Log Left in Production Code
Found in:
- `UI.applyUISettings` (line 352)
- `UIView.show/hide/Awake/Dispose` (lines 83, 94, 110, 125)
- `ViewManager.Dispose` (line 30)

**Fix:** Remove or wrap in `#if UNITY_EDITOR`.

### 20. `UI.Instantiate<T>` — Throws Outside Play Mode
Throws `"Component can only be created dynamically at runtime!"` but `UIBase.create()` doesn't check this, leading to confusing errors when called from editor scripts.

**Fix:** Add play mode check in `create()` with a clearer error message.

### 21. `construct()` — Deep Recursion
No depth limit. Deep hierarchies could cause stack overflow.

**Fix:** Convert to iterative traversal with an explicit stack.

`Expression.MemberInit` copies all fields/properties from source. For large structs, this is expensive. Property getters with side effects could cause bugs.

**Fix:** Only copy the changed property (requires mutable struct or `with` expression — C# 10+).

### 23. `GetMemberName` — Limited Expression Support
Only handles simple member access and unary expressions. Computed properties or method calls throw `InvalidExpressionException`.

**Fix:** Document the limitation, or support more expression types.

# Architectural Overview

## High-Level Structure

The entire runtime library lives under `Assets/Runtime/` in 8 subsystems:

```
Assets/Runtime/
├── Core/         → Singleton, base classes, view management, bootstrapping
├── Components/   → Reusable UI components (Button, Text, Icon, Switch, Slider, etc.)
├── Views/        → Full-screen overlay views (Dialog, Snackbar, Tooltip)
├── Themes/       → ScriptableObject-based theming (colors, typography, spacing)
├── Data/         → Data binding engine (Binder<T>)
├── Extensions/   → C# extension methods
├── Rendering/    → SDF rendering, Material Symbols, custom layout groups
└── Utility/      → Object pooling (sync + async)
```

## Core Subsystem (`Core/`)

The foundation layer that everything else builds on:

| File | Role |
|------|------|

Owns the UI root GameObject, 4 Canvas layers (BACKGROUND, DEFAULT, MENU, POPUP), the UI element cache (`Dictionary<string, IUI>`), the `ViewManager`, `UISettings`, and the static object pool. # Core Systems — Deep Dive

## 1. UI Singleton (`UI.cs`)

The central facade and service locator. Responsibilities:

**Canvas Management**
- Creates a root GameObject `"UI"` with 4 child Canvases: `BACKGROUND`, `DEFAULT`, `MENU`, `POPUP`
- Each Canvas uses `ScreenSpaceOverlay` + `ConstantPixelSize` scaling
- `sortingOrder = layerId + 3` ensures correct z-ordering between layers
- A hidden `"Cached UI Elements"` GameObject holds pooled components

**Element Cache**
- `Dictionary<string, IUI> _uiElements` — maps GUIDs to all live UI elements
- Cache is invalidated on `Awake`/`OnDestroy` of any `UIBase` via `UI.invalidateCache()`
- Invalidation is debounced: only one rebuild per frame, executed at end-of-frame via `UniTask.WaitForEndOfFrame`
- Rebuild uses `GetComponentsInChildren<IUI>(true)` (includes inactive) and detects duplicate IDs

**Instantiation Pipeline**
- `Instantiate<T>()` loads prefab via Addressables (keyed by `typeof(T).FullName`), then calls `create(prefab, parent)`
- `create()` instantiates on the correct Canvas layer (views go to their `_canvasLayer`, components to `DEFAULT` or a provided parent)
- `construct()` recursively traverses children first (post-order), then calls `Constructor()` on each `IUI` — ensures children are initialized before parents

**Pool Pre-warming**
- Static constructor reflects over all `IUIComponent` types in the assembly
- For each type with `preCacheCount > 0`, loads the prefab via Addressables and pre-creates that many instances into the hidden cache GameObject
- All pre-cached instances are immediately `Dispose()`d (returned to pool)

**Query System**
- `UI.Query<T>()` returns a `UIQuery<T>` wrapping `_uiElements.Values.OfType<T>()` — O(n) over cached dictionary
- `UIExtension.Query<T>(this IUI parent)` filters to elements whose `rectTransform.IsChildOf(parent.rectTransform)` — scoped queries without `GetComponentsInChildren`

**Theme Propagation**
- `applyUISettings()` iterates all non-pooled elements, calls `setupUI()` + `refresh()` on each
- Triggered by `UISettings.onChanged` event

## 2. UIBase<TUI, TData> (`UI.cs`)

Abstract base for all UI elements. The CRTP (Curiously Recurring Template Pattern) is used for static per-type pooling.

**Static Pool**
- `private static PoolAsync<TUI> _pool` — one pool per closed generic type (e.g., `Button` gets its own pool, `Text` gets its own)
- Factory: `() => UI.Instantiate<TUI>()` — async Addressables load
- Reset: `instance => instance._isPooled = true`

**create() Flow**
1. `_pool.get()` — get from pool (or grow)
2. `SwitchToMainThread` — Unity API requirement
3. `UI.views?.currentContext?.register(instance)` — register with active ViewContext for lifecycle management
4. Set parent (explicit parent, or current view's mainView, or DEFAULT canvas)
5. `SetAsLastSibling()` — render on top within parent
6. `_isPooled = false`, `SetActive(true)`
7. If data provided, set `binder.data`
8. Optional `postConstruct` async callback

**Constructor() Flow**
1. Generate GUID if in play mode
2. Cache `rectTransform`
3. Clear binder events and bindings
4. Call `setupUI(UI.settings)` — subclass hook
5. Wire `onBindingChanged`/`onBindingCompleted` to sync `_data` field (for editor serialization)
6. Set `binder.data = _data` — triggers initial binding refresh
7. Invalidate UI cache

**Dispose()**
- If already pooled, no-op
- Return to pool via `_pool.free((TUI)this, true)` — `addToPool=true` because the instance was created outside the pool (via `Instantiate`)
- `SetActive(false)` — pool convention

## 3. Binder<TData> (`Data/Binder.cs`)

High-performance data binding engine using compiled expression trees.

**Architecture**
- `Dictionary<string, Action<object>> _bindings` — maps property name → UI update callback
- `Dictionary<string, List<string>> _dependencies` — maps property name → list of properties that depend on it
- Static `BinderCache` — `ConcurrentDictionary<string, Func<TData, object>>` for getters and `ConcurrentDictionary<string, Func<TData, object, TData>>` for setters, shared across all `Binder<TData>` instances

**Binding**
```csharp
binder.bind(
    data => data.Health,           // property expression
    value => slider.value = value, // UI update action
    data => data.MaxHealth         // dependency
);
```
- Property expression is compiled once and cached statically
- Setter is compiled using `Expression.MemberInit` — creates a new struct with the changed property and all others copied from source (immutable update pattern)
- Dependencies tracked for cascading updates

**Update Flow**
- `data = newValue` → iterates all bindings, calls `refreshBinding()` for each
- `updateField(expr, newValue)` → compiles setter, creates new struct, refreshes only that binding + dependents
- `refresh()` → refreshes all bindings + their dependents
- `reset()` → restores `_initial` value

**Circular Dependency Detection**
- DFS traversal of the dependency graph before adding a new edge
- Throws `InvalidOperationException` if a cycle would be created

**Performance Characteristics**
- Getters/setters compiled once per property per type, cached in static `ConcurrentDictionary`
- Updates are direct delegate calls — no reflection at runtime
- `updateField()` is the recommended high-performance path (only refreshes one binding)

## 4. View System

### UIView<TView, TData> (`UIView.cs`)

Abstract base for overlay views (Dialog, Snackbar, Tooltip).

**State Machine**
- `ViewState`: `CREATED` → `VISIBLE` → `HIDDEN` → `DESTROYED`
- `show()`: activates GameObject, forces layout rebuild, sets VISIBLE, fires `onShow`
- `hide()`: deactivates GameObject, sets HIDDEN, fires `onHide`
- `close()`: fires `onClose` only (actual disposal handled by ViewManager/ViewContext)
- Sticky views (`_isSticky = true`) ignore `hide()` — they persist across view transitions

**Static open/openAsync**
- Delegates to `UIBase.create(null, data, postConstruct)` — views have no parent, they go to their canvas layer

### ViewManager (`ViewManager.cs`)

Stack-based navigation manager.

**Data Structures**
- `Stack<ViewContext> _viewStack` — active view stack
- `ConcurrentDictionary<Type, ViewContext> _pendingViewContexts` — reusable contexts for popped views
- `CancellationTokenSource _contextSwitchCTS` — cancelled on every push/pop to abort in-flight transitions

**pushAsync Flow**
1. Cancel previous CTS, create new one
2. Deactivate current top view (`setActive(false, false)`) — animate out
3. Check `_pendingViewContexts` for reusable context of this type
4. If no reusable context, create new `ViewContext`
5. Push context onto stack
6. If context has no mainView, create one via `UIView.create()` and wire `onClose` → `pop()`
7. If reusing, update data and call postConstruct
8. Activate new context (`setActive(true, false)`) — animate in

**popAsync Flow**
1. Cancel previous CTS, create new one
2. Pop context from stack
3. `setActive(false, disposeContext)` — animate out, optionally dispose
4. If not disposing, store in `_pendingViewContexts` for reuse
5. Reactivate new top view (`setActive(true, false)`)

**Context Reuse**
- Popped views are cached by type in `_pendingViewContexts`
- Next push of same type reuses the context (and its mainView instance)
- Avoids repeated instantiation/disposal of the same view type

### ViewContext (`ViewContext.cs`)

Per-view lifecycle owner.

**Responsibilities**
- Owns a `mainView` (IView) and `List<IUI> _ownedElements`
- `register(IUI)` — called by `UIBase.create()` to register any component created while this context is active
- `setActive(bool, bool, CancellationToken)` — coordinates show/hide with DOTween transitions

**setActive Flow**
1. Kill existing tweens on mainView's rectTransform
2. If activating:
   - Get `transitionIn()` tween (currently returns null — transitions disabled)
   - If tween exists: set target, `OnStart` → `show()`, `OnComplete` → signal `UniTaskCompletionSource`
   - If no tween: just call `show()`
3. If deactivating:
   - Get `transitionOut()` tween
   - If tween exists: `OnComplete` → `hide()` + optional `Dispose()`
   - If no tween: `hide()` + optional `Dispose()`
4. Await completion with cancellation support

**Dispose**
- Kills tweens, disposes all owned elements in reverse order

### ViewTransitionEffects (`ViewTransitionEffects.cs`)

DOTween-based transition animations as extension methods on `IView`.

**Available Effects**
- `fadeIn/fadeOut` — alpha 0↔1 on CanvasGroup
- `slideXIn/slideXOut` — anchoredPosition X from/to screen edge
- `slideYIn/slideYOut` — anchoredPosition Y from/to screen edge
- `zoomIn/zoomOut` — localScale 0↔1

**Current State**
- `transitionIn()` and `transitionOut()` return `null` — the composite sequence logic is commented out
- Individual effects are available but not composed automatically
- `ViewTransition` flags enum (FADE, SLIDE_X, SLIDE_Y, ZOOM) is defined but not yet wired into the composite methods

## 5. Object Pooling

### Pool<T> (`Utility/ObjectPool.cs`)

Synchronous generic pool.

**Design**
- `List<T> available` — items ready for use
- `List<T> pool` — all items managed (available + in-use)
- `get()` — pops from available, grows by 1 if empty
- `free()` — returns to available (validates item belongs to pool)
- `grow(n)` — creates n new items via factory
- `freeAll()` — returns all items to available

**GameObjectPool** (subclass)
- `get()` — calls `base.get()` then `SetActive(true)`
- `freeInternal()` — `SetActive(false)` then `base.freeInternal()`
- `add()` — creates new element, `SetActive(false)` immediately

### PoolAsync<T> (`Utility/ObjectPoolAsync.cs`)

Async pool using UniTask.

**Key Difference from Pool<T>**
- Factory is `Func<UniTask<T>>` — supports async creation (e.g., Addressables loading)
- `get()` returns `UniTask<T>` — awaits grow if needed
- `free()` has `addToPool` parameter — allows adding external items to the pool (used by `UIBase.Dispose()` for instances created via `Instantiate` outside the pool)

**Usage in UIBase**
- `PoolAsync<TUI>` factory: `() => UI.Instantiate<TUI>()` — async Addressables load
- Reset: `instance => instance._isPooled = true`
- `Dispose()` calls `_pool.free((TUI)this, true)` — `addToPool=true` because the instance was created via `Instantiate` (not from pool), so it needs to be added to the pool's tracking list

## 6. UIBootstrapper (`UIBootstrapper.cs`)

Runtime initialization via `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterSceneLoad)]`.

**Flow**
1. Load `UISettings` from `Resources/Settings/UISettings`
2. Clone it (`uiSettings.clone()`) — runtime instance is separate from the asset
3. Create `UI` singleton with the cloned settings
4. Set camera background to `Surface5` color
5. Wire `onChanged` to update camera background on theme changes

**Why AfterSceneLoad?**
- Ensures all scene objects exist before UI system initializes
- `SubsystemRegistration` on `UI.InitializeOnLoad` handles script reload state reset

## 7. UIQuery<T> (`UIQuery.cs`)

Lightweight query wrapper.

**API**
- `First()` — `FirstOrDefault()`
- `AtIndex(int)` — `ElementAtOrDefault()`
- `ToList()` — materialize to list
- Implements `IEnumerable<T>` — supports LINQ

**Performance**
- Wraps the pre-built `_uiElements` dictionary values — no `GetComponentsInChildren` calls
- `OfType<T>()` is a single pass over all elements
- Scoped queries (`UIExtension.Query<T>(parent)`) add an `IsChildOf` filter

## Key Architectural Insights

1. **CRTP for static pooling** — `UIBase<TUI, TData>` gives each closed generic type its own static `_pool` without a central pool registry
2. **Post-order construction** — `construct()` initializes children before parents, ensuring child references are valid when parent's `Constructor()` runs
3. **Debounced cache invalidation** — multiple `Awake`/`OnDestroy` calls in one frame trigger only one cache rebuild at end-of-frame
4. **Immutable struct updates** — `Binder` setters create new structs via `Expression.MemberInit`, preserving value semantics
5. **Context reuse** — `ViewManager` caches popped `ViewContext` instances by type, avoiding repeated view instantiation
6. **Cancellation-driven transitions** — every push/pop cancels the previous CTS, ensuring only the latest transition runs
7. **Addressables integration** — all prefabs loaded by type name, enabling async loading and memory management
